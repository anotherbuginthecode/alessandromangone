## Swipe apps optimise for the chat. Matcha optimises for the table.

Most dating apps measure success in messages. Matcha measures it in dates that actually happen. Two people like each other, each pays €10, which covers a drink, each picks the evenings they are free, and Matcha books a table at a partner venue in Milan. A short chat opens two hours before the date and closes an hour after it. There is no endless chat to get lost in.

I co-founded Matcha with two partners. I own everything technical: the architecture, the code and the way it gets delivered.

## Real money, strangers meeting in person, no backend team

A dating app that ends at a real table carries more weight than a chat app. From the first release we needed:

- Payments that become real only when the payment provider says so.
- Two people's free evenings matched without either one seeing the other's.
- Identity checks, reports, blocks and moderation, because strangers meet face to face.
- A venue network run by one person, without building a custom CRM.
- All of it shipped by one engineer and a board of coding agents.

## The app may express intent. Only the server records facts.

The mobile app is a thin client built with Expo and React Native. It has no backend of its own: it talks to Supabase with the user's session and nothing more. Postgres is the single source of truth. The app can like a profile, submit free evenings or send a chat message. It cannot mark a match as paid, change its status, grant a credit or suspend anyone. Database permissions enforce that, not code review.

## A match is a state machine, not a conversation

Every match moves through a fixed set of states, and the app writes none of them. Both people share a single 24-hour clock from the moment they match. Paying comes before picking evenings on purpose: the payment is the moment you commit, and it filters out the matches nobody meant to keep.

## Manual first, on purpose

The first design had an algorithm that rotated venues, with availability tables and capacity data. We had none of that data, no tooling on the venue side and one person running operations. So a later decision record cut it from the first release: a person books every venue by hand.

Airtable is the operators' work queue. A button on a row calls the server to confirm a booking or act on a report, and that call is what moves the match forward. Slack is the alarm bell when money or safety needs a human. The algorithm is deferred, not deleted: it gets built when the number of venues and dates justifies it.

## Built by a board, reviewed by people

Matcha is mostly written by coding agents working a GitHub board. A short file in the repository, `AGENTS.md`, sets the rules: every issue carries one area label and one autonomy label, and the label decides how far an agent can go alone.

<Quote source="AGENTS.md">A task is ready when a new agent can finish it without asking product or technical questions.</Quote>

<AgentBoard />

The classification is a rubric, and the first match wins. An issue is supervised when it touches authentication, the database schema, money or personal data, security settings, deployment, a published API contract, untrusted content, anything a revert cannot undo, or when it is the first of its kind and sets a pattern others will copy. Everything else runs on auto. An agent may raise an issue from auto to supervised, never the other way round. When it is stuck, it writes the problem, the options and a recommendation, flags the issue for a human and stops.

Two things keep the agents honest. The decision records and the architecture document carry context from one session to the next, and agents update them when they change ownership, data or trust boundaries. Continuous integration runs linting, type checks and unit tests on every pull request, then applies every migration to a separate test project and runs an end-to-end suite against it.

## The leverage is in the rules, not the prompts

Most of Matcha's code was written by agents, and it still reads like one engineer's decisions. That is what the setup is for. The rubric decides what an agent may do alone. The database permissions make the wrong write impossible instead of merely unlikely. The decision records keep the reasoning alive between sessions. Prompts change every week; those rules are what let three founders ship like a bigger team.
